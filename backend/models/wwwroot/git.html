01
Git e GitHub (sem confusão)
Git é o programa que salva o histórico do seu projeto no seu computador.
GitHub é o site onde esse projeto fica online para você colaborar e ter uma cópia na nuvem.
Com comandos do Git, você envia alterações, baixa atualizações, consulta versões e gerencia o que está no GitHub.
💡 Git: histórico no seu PC. GitHub: histórico na internet.
02
Onde rodar os comandos (antes de começar)
Quando um slide mostrar um bloco de comandos, você vai usar um terminal. Terminal é a “telinha de comandos” onde você cola e executa linhas como git status.
Opção mais fácil (recomendada): Terminal do VS Code
1) Abra a pasta do projeto: Arquivo → Abrir pasta…
2) Abra o terminal: Terminal → Novo terminal (atalho comum: Ctrl+`)
3) Cole o comando (um por vez) e aperte Enter
Outras opções (também funciona):
- Windows: PowerShell ou Prompt de Comando (CMD)
- macOS: Terminal
- Linux: Terminal
Importante: antes de rodar comandos do Git, esteja na pasta do projeto. Exemplo no Windows: cd C:\caminho\do\seu\projeto
💡 Regra de ouro: comandos do Git vão no terminal — de preferência o terminal do VS Code com a pasta do projeto aberta.
03
Instalar o Git (e conferir se funcionou)
Windows (mais comum para iniciantes): baixe o instalador em git-scm.com/download/win, execute e avance com Next até finalizar. Isso instala o Git e um terminal chamado Git Bash (útil no dia a dia).
macOS: você pode instalar pelo instalador no site do Git ou, se já usa Homebrew, usar brew install git.
Linux (Debian/Ubuntu): normalmente instala pelo gerenciador de pacotes com sudo apt install git.
Depois de instalar: abra um terminal (de preferência o do VS Code, como no slide anterior) e rode git --version. Se aparecer um número de versão, está ok.
# Windows → https://git-scm.com/download/win (instalador)
#
# macOS (Homebrew)
brew install git
#
# Linux (Debian/Ubuntu)
sudo apt install git
#
# Conferência (qualquer sistema)
git --version
💡 No Windows, você pode usar Git Bash ou o terminal do VS Code. Nos dois, git --version deve funcionar depois da instalação.
04
Configurando o Git: gerando sua identidade
Em todo commit, o Git registra quem fez a mudança: um nome e um e-mail. Por isso você diz ao Git “quem você é” antes de trabalhar com repositórios.
Com --global, essas informações ficam salvas na sua máquina e valem para todos os projetos (não só para uma pasta).
Onde rodar: qualquer terminal que já esteja funcionando com Git — por exemplo Git Bash, PowerShell ou o terminal do VS Code. Para --global, você não precisa estar dentro da pasta de um projeto.
Cole os comandos abaixo e troque o texto entre aspas pelo seu nome e pelo seu e-mail.
git config --global user.name "Seu Nome" git config --global user.email "seu@email.com"
💡 Prefira o mesmo e-mail da sua conta GitHub para seus commits aparecerem ligados ao seu perfil.
05
Primeiro repositório na sua máquina (git init)
Um repositório Git é uma pasta de projeto em que o Git passa a guardar o histórico. Por baixo dos panos aparece uma pasta oculta chamada .git (é lá que fica esse histórico).
Use git init quando você já tem uma pasta com arquivos e quer começar a versionar do zero nela (ainda não existe histórico Git ali).
Antes dos comandos: entre na pasta do projeto no terminal (como no Slide 02). No exemplo abaixo, meu-projeto é só um nome fictício — troque pelo nome da sua pasta.
(Obs.: neste guia, o que vier depois de # em cada linha é só comentário explicando a utilidade daquele comando — não copie essa parte.)
cd meu-projeto# entra na pasta do projeto
git init# começa o Git nessa pasta
💡 Depois do git init, aparece a pasta oculta .git — não apague ela; é onde o Git guarda o histórico.
PAUSA
Muita coisa de uma vez, né? Mas relaxa — você não precisa virar “mestre do Git” hoje.
💡 Vai no passo a passo: entenda onde rodar e o que cada comando faz. O resto vem na prática.
06
Salvar mudanças no histórico (status → add → commit)
Depois do git init, o dia a dia é um ciclo: ver o que mudou → marcar o que vai entrar no próximo salvamento → registrar esse salvamento no histórico com uma mensagem.
Em termos simples: você edita arquivos na pasta (trabalho); o git add define o que será incluído no próximo commit (stage); o git commit cria um registro no histórico (commit) com autor, data e mensagem.
Rode os comandos na pasta do repositório, no terminal do VS Code/Cursor (como no Slide 02).
No primeiro commit, uma mensagem simples como “Primeiro commit” já vale. Em times, é comum usar prefixos como feat:, fix: ou docs: na mensagem — no Slide 07 você vê o significado de cada um e exemplos para copiar.
git status# mostra o que mudou e o que já está preparado para commit
git add .# prepara todas as mudanças para o próximo commit
git commit -m "Primeiro commit"# registra no histórico
💡 A mensagem do commit é o “rótulo” da mudança: quanto mais clara, mais fácil de entender depois.
07
Nomenclatura das mensagens de commit (feat, fix, docs…)
No Slide 06 apareceram prefixos como feat:, fix: e docs:. Eles fazem parte de convenções muito usadas (a mais conhecida é Conventional Commits): um jeito padronizado de escrever a mensagem para o histórico ficar legível e ferramentas conseguirem montar changelogs ou releases com menos trabalho manual.
Formato típico: tipo: descrição curta. Em geral a descrição vem no imperativo ou como “o que o commit faz” (adiciona, corrige, atualiza…), sem ponto final no final da primeira linha.
Prefixos que você mais vai ver:
• feat: — nova funcionalidade para quem usa o sistema
• fix: — correção de bug ou comportamento incorreto
• docs: — só documentação (guias, comentários de documentação)
• style: — formatação, espaços, aspas (sem mudar lógica)
• refactor: — reorganização interna do código sem mudar o que o usuário percebe
• test: — incluir ou ajustar testes automatizados
• chore: — manutenção “de bastidor” (dependências, scripts de build, configs que não são feature nem fix)
• perf: — melhoria de desempenho
Opcional — escopo entre parênteses: quando ajuda a localizar o pedaço do projeto: feat(auth): login com OAuth, fix(api): erro 500 na listagem.
git commit -m "feat: adiciona filtro por data no relatório"
git commit -m "fix: impede erro quando a lista está vazia"
git commit -m "docs: atualiza guia de instalação"
💡 Projeto pessoal pode usar mensagem livre; em time ou open source, esse padrão reduz “cadê o commit que corrigiu X?” e padroniza revisões.
08
Criando seu repositório no GitHub (no site)
1) Acesse o GitHub e clique em New repository (às vezes aparece como Repositories → New).
2) Escolha um Repository name simples (ex.: meu-projeto) e defina se será Public ou Private.
3) Se você já tem o projeto no computador e vai enviar pela primeira vez, evite criar arquivos automáticos agora: não marque “Add a README”, nem adicione .gitignore ou licença neste momento (isso reduz dor de cabeça no primeiro push).
4) Clique em Create repository. Na página do repositório, use o botão verde Code e copie a URL HTTPS (algo como https://github.com/USUARIO/REPO.git) — você vai colar no terminal no próximo slide.
💡 Primeiro você cria o repositório no GitHub. No próximo slide, você conecta sua pasta local a ele e envia seu primeiro push.
09
Conectar seu projeto ao GitHub (remote + primeiro push)
Objetivo: ligar o repositório da sua máquina ao repositório que você criou no GitHub e enviar seus commits de lá pra cá (primeiro push). Para isso, já ajuda ter pelo menos um commit local feito (como no Slide 06).
No terminal, esteja na pasta do projeto (VS Code aberto na pasta certa, como no Slide 02). Use a mesma URL HTTPS que você copiou no Slide 08 (troque USUARIO e REPO ou cole a URL inteira).
O comando git remote add origin ... cria o apelido origin: um atalho para o endereço do GitHub.
O git push -u origin main envia a branch main. Se a sua branch principal tiver outro nome (ex.: master), troque no comando.
(Obs.: Rode um comando por vez. Copie e cole o comando no terminal e aperte Enter.)
git remote add origin https://github.com/USUARIO/REPO.git
git remote -v # Confirma se o remote foi adicionado corretamente
git push -u origin main# primeiro envio
💡 Depois do primeiro push com -u, nos próximos envios normalmente basta usar git push (sem repetir origin main).
10
Branches: trabalhar sem bagunçar a main
Uma branch é uma linha de desenvolvimento paralela. Você pode trabalhar em uma feature/correção sem mexer direto na main até estar pronto para juntar.
git branch nome só cria a branch; você continua na branch atual. Já git checkout -b nome cria e entra na branch (no Git mais novo existe também git switch -c nome).
Fluxo típico: criar a branch → fazer commits nela → voltar pra main → integrar (muitas vezes via Pull Request no GitHub).
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
git checkout -b minha-feature# criar e entrar na branch
git branch# listar branches
git checkout main# voltar pra main
git merge minha-feature# juntar à main
💡 Em equipes, o hábito saudável é evitar commit direto na main e usar uma branch por tarefa ou correção.

11
Atualize seu projeto antes de começar (pull / fetch)
Antes de criar uma branch nova ou continuar uma tarefa, é bom garantir que você está com a versão mais recente do GitHub.
git pull baixa e já tenta integrar as mudanças na sua branch atual. git fetch só baixa as informações; você olha com calma antes de aplicar.
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
git checkout main# volta para a main antes de atualizar
git pull# baixa atualizações e integra na branch atual
git fetch# alternativa: só baixa infos, sem integrar
💡 Fazer pull antes de começar reduz muito a chance de conflito lá na frente.
12
Depois de desenvolver: push da sua branch e abrir um Pull Request (PR)
Quando você termina uma parte da tarefa na sua branch, você envia pro GitHub e abre um PR para revisar e juntar na main.
PR (Pull Request) é a “solicitação para juntar” sua branch na branch principal, com descrição do que mudou e como testar.
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
git status# confira se está tudo certo antes de enviar
git push -u origin minha-branch# envia sua branch (primeira vez com -u)
No GitHub (navegador), normalmente aparece um botão Compare & pull request depois do push. Clique, preencha título e descrição e finalize em Create pull request.
💡 PR serve para revisão e histórico: descreva o que mudou e como testar.
13
Deu conflito? O que é e como resolver:
Conflito acontece quando duas mudanças mexem nas mesmas linhas e o Git não consegue juntar sozinho.
Você vai ver marcações no arquivo (ex.: <<<<<<<, =======, >>>>>>>).
Como resolver: abra o arquivo no editor, escolha o resultado final, apague os marcadores, salve e depois marque como resolvido com git add. Por fim, finalize com um commit.
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
git status# mostra quais arquivos estão em conflito
git add arquivo-em-conflito# marca o arquivo como resolvido
git commit -m \"resolve conflito\"# finaliza a resolução
💡 Conflito não é “erro”: é só o Git pedindo para você decidir a versão final daquele trecho.
14
Como fazer o merge no GitHub (pelo Pull Request)
Depois que sua branch foi enviada e o PR está aberto, o merge é o passo de juntar essa branch na main.
No GitHub (navegador), entre no seu Pull Request e verifique: se está tudo verde (checks/CI), se teve aprovação quando existir review, e se não aparece “Conflicts”.
Quando estiver ok, clique em Merge pull request (ou o botão equivalente), confirme a mensagem e finalize.
Depois do merge, o GitHub normalmente oferece Delete branch — pode apagar a branch remota para manter o repositório organizado.
💡 Merge no GitHub mantém revisão e histórico: sempre descreva bem o PR e só faça merge quando estiver tudo ok.
15
.gitignore: o que é e o que colocar nele
.gitignore é um arquivo que diz ao Git quais arquivos/pastas ele deve ignorar (não entrar em commit).
Ele serve para não versionar coisas geradas automaticamente, arquivos locais da sua máquina e segredos (como senhas e tokens).
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
node_modules/# dependências baixadas automaticamente
.env# variáveis de ambiente (não subir)
dist/# build gerado
*.log# logs
💡 Regra de ouro: se o arquivo é gerado automaticamente ou é segredo, ele não deve ir para o Git.
PAUSA
Se você chegou até aqui, já tá voando. Daqui a pouco isso vira reflexo.
💡 O segredo é o ciclo: pull da main → editar → add → commit → push → PR. Repete e pronto.
16
Comandos úteis do dia a dia (diff e log)
Antes de commitar ou abrir PR, vale conferir o que mudou e o histórico recente.
git diff mostra mudanças ainda não “preparadas”; git diff --staged mostra o que já está no stage. git log --oneline -5 mostra os últimos 5 commits de forma compacta.
(Obs.: o que vier depois de # é só comentário — não é obrigatório copiar essa parte.)
git diff# mudanças ainda não staged
git diff --staged# mudanças já no stage
git log --oneline -5# últimos 5 commits (você pode mudar o número de commits)
💡 Use git diff antes de commitar para evitar surpresa no que vai entrar no histórico.
